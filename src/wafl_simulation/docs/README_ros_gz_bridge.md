# `ros_gz_bridge.yaml` — Gazebo Harmonic <-> ROS 2 Jazzy topic bridge

Configuration for `ros_gz_bridge`'s `parameter_bridge`, in `wafl_simulation/config/`. It is loaded by `gazebo.launch.py`:

```
parameter_bridge --ros-args -p config_file:=<this file>
```

The related file `config/sim_controllers.yaml` (wheel mode and controller gains) is explained in [README_sim_controllers.md](README_sim_controllers.md).

## How the bridge works (in one minute)
Gazebo and ROS 2 use **different message systems**. `parameter_bridge` copies messages between a Gazebo topic and a ROS topic, converting the type. **One entry in the YAML = one bridged topic.** If a topic is not listed, ROS cannot see it (and Gazebo cannot see the ROS one).

## The variables of one entry

```yaml
- ros_topic_name: "/front_left_wheel_cmd_vel"
  gz_topic_name:  "/model/wafl/joint/front_left_wheel_joint/cmd_vel"
  ros_type_name:  "std_msgs/msg/Float64"
  gz_type_name:   "gz.msgs.Double"
  direction:      ROS_TO_GZ
```

| Variable | Meaning |
|----------|---------|
| `ros_topic_name` | Name the topic has on the ROS 2 side. This is what `base_controller`, Nav2, the dashboard etc. use. |
| `gz_topic_name` | Name on the Gazebo side. It must match **exactly** what the plugin or sensor in `urdf/wafl_gz_plugins.xacro` uses (`<topic>` / `<odom_topic>`). A mismatch silently does nothing. Check with `gz topic -l`. |
| `ros_type_name` | ROS message type, written `package/msg/Name`. |
| `gz_type_name` | Gazebo message type, written `gz.msgs.Name`. The pair must be a supported combination (see the table below). |
| `direction` | `GZ_TO_ROS`: data flows out of the sim (sensors, odometry). `ROS_TO_GZ`: commands flow into the sim. `BIDIRECTIONAL`: both (not used here). |

Supported type pairs used in this file:

| ROS type | Gazebo type |
|----------|-------------|
| `rosgraph_msgs/msg/Clock` | `gz.msgs.Clock` |
| `sensor_msgs/msg/LaserScan` | `gz.msgs.LaserScan` |
| `sensor_msgs/msg/Image` | `gz.msgs.Image` |
| `sensor_msgs/msg/Imu` | `gz.msgs.IMU` |
| `nav_msgs/msg/Odometry` | `gz.msgs.Odometry` |
| `sensor_msgs/msg/JointState` | `gz.msgs.Model` |
| `std_msgs/msg/Float64` | `gz.msgs.Double` |

## Name contracts
| Item | Value |
|------|-------|
| World name | `warehouse` (`/world/warehouse/...`) |
| Model name | `wafl` (`/model/wafl/...`) |

The Gazebo-side topics are produced or consumed by the robot plugins (`urdf/wafl_gz_plugins.xacro`, generated by `scripts/generate_assets.py`) and `worlds/warehouse.world`. If you rename a topic here, change it there too.

## Gazebo -> ROS (`GZ_TO_ROS`)

| ROS topic | Gazebo topic | ROS type | Notes |
|-----------|--------------|----------|-------|
| `/clock` | `/clock` | `rosgraph_msgs/Clock` | Required: every `use_sim_time` node stalls without it. |
| `/scan` | `/lidar/scan` | `sensor_msgs/LaserScan` | RPLiDAR A2M8-like, frame `laser_link`. |
| `/camera/image_raw` | `/camera/image` | `sensor_msgs/Image` | Kinect v1 RGB, 640x480 rgb8, frame `camera_link`. |
| `/camera/depth/image_raw` | `/camera/depth` | `sensor_msgs/Image` | Depth, 32FC1 in **metres**. |
| `/imu` | `/imu` | `sensor_msgs/Imu` | Raw sim IMU. Hardware publishes `/imu/data` instead. In sim it goes through `odom_covariance_fix` to `/imu_fixed`. |
| `/odom` | `/model/wafl/odometry` | `nav_msgs/Odometry` | From `OdometryPublisher` (ground truth). `frame_id: odom`, `child_frame_id: base_footprint`, **zero covariance**, so it goes through `odom_covariance_fix` to `/odom_fixed` and then the EKF. |
| `/joint_states` | `/world/warehouse/model/wafl/joint_state` | `sensor_msgs/JointState` | Gazebo type is `gz.msgs.Model`. Feeds `robot_state_publisher` and `sim_fork_adapter`. |

## ROS -> Gazebo (`ROS_TO_GZ`) — the per-joint actuation contract

All are `std_msgs/Float64` <-> `gz.msgs.Double`. They are published only by `base_controller` (after arbitration) and `sim_fork_adapter`.

| ROS topic | Gazebo topic | Unit | Joint(s) it moves |
|-----------|--------------|------|-------------------|
| `/front_steer_cmd_pos` | `/model/wafl/front_steer/cmd_pos` | rad (alpha) | `front_left_steer_joint` **and** `front_right_steer_joint` (both subscribe to the same topic, so they stay parallel like the real chain/sprocket) |
| `/castor_cmd_pos` | `/model/wafl/joint/caster_joint/cmd_pos` | rad (beta) | `caster_joint`, the **rear** steering. The "castor" spelling is kept on purpose to match README §4.3 / §7 |
| `/front_left_wheel_cmd_vel` | `/model/wafl/joint/front_left_wheel_joint/cmd_vel` | rad/s | `front_left_wheel_joint` (rad/s = speed / `wheel_radius`) |
| `/front_right_wheel_cmd_vel` | `/model/wafl/joint/front_right_wheel_joint/cmd_vel` | rad/s | `front_right_wheel_joint` |
| `/fork_cmd_vel` | `/model/wafl/joint/fork_joint/cmd_vel` | m/s, + = up | `fork_joint`, written by `sim_fork_adapter` |

The rear wheel's spinning joint (`caster_wheel_joint`) has **no** topic on purpose: it is passive and must roll freely.

## Deliberately NOT bridged
- **`/model/wafl/tf*`.** The EKF is the only publisher of `odom -> base_footprint`. The plugin's TF is sent to `/model/wafl/tf_unused_ekf_owns_odom_tf`, which is never bridged.
- **`/cmd_vel`.** Gazebo must never read raw `/cmd_vel`, so manual, fork and dock commands cannot bypass the e-stop and priority logic.
- **`/cmd_vel_out`.** **Removed.** It fed the old DiffDrive plugin, which cannot model steered wheels and no longer exists.

## Adding a topic
Append an entry:

```yaml
- ros_topic_name: "/my_topic"
  gz_topic_name: "/model/wafl/my_topic"
  ros_type_name: "std_msgs/msg/Float64"
  gz_type_name: "gz.msgs.Double"
  direction: GZ_TO_ROS      # or ROS_TO_GZ (or BIDIRECTIONAL)
```

Then update the Master Topic Index in the main README, and rebuild and relaunch.

## Debugging
```bash
gz topic -l                    # topics on the Gazebo side
ros2 topic list -t             # topics on the ROS side
ros2 topic hz /scan            # check sensor data flows
ros2 topic echo /clock --once  # check the clock bridge
# drive one wheel by hand (kinematic mode):
ros2 topic pub -r 10 /front_left_wheel_cmd_vel std_msgs/msg/Float64 "{data: 3.0}"
```
If a ROS topic is missing, check that the Gazebo topic name matches the plugin config exactly (`gz topic -l`) and that the ROS/Gazebo message type pair is a supported combination.
